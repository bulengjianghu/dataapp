# 分流节点设计

## 1. 设计背景

在交互规则体系中，当前“条件节点 + true/false 两条边”的模型更接近传统 `if/else`，适合二叉判断，但在以下场景下表达力不足：

- 一个触发后需要按多个条件分别进入不同子链路
- 某些条件可以同时命中，并分别执行各自的联动逻辑
- 规则配置希望保持“执行路径”心智，而不是直接暴露为并行规则集合

基于上述场景，规则编辑器可引入“分流节点”模型，用于承载多路分流能力。

## 2. 设计结论

分流节点模型是合理的，且在“表达力”和“结构约束”之间取得了较好的平衡。

但需要明确：

- 该模型不是传统“二选一/多选一”的分支模型
- 该模型更接近“树状分流 / 河道分发”模型
- 到达分流节点后，可能同时进入多条子链路
- 分流后的链路不允许再次汇合

因此，产品命名建议使用“分流节点”，不建议继续使用“分支节点”，以免用户误解为互斥择一路径。

## 3. 核心概念

### 3.1 节点类型

- 普通节点：`trigger / query / transform / command / context / notice` 等执行节点
- 分流节点：仅负责将执行流分发到多条后续线路，本身不直接承载具体判断条件

### 3.2 连线类型

连线本身具备类型，分为两类：

- 直接流转
- 条件流转

### 3.3 整体模型

整套规则图可理解为一个树状河道模型：

- 普通节点沿主链顺序执行
- 到达分流节点后，执行流可以流向多条子河道
- 子河道一旦分开，不允许再次汇合

## 4. 基础规则

### 4.1 普通节点的连线约束

- 非分流节点只能接出“直接流转”连线
- 普通节点执行完成后，必然沿其唯一的直接流转边进入下一个节点

这保证普通节点始终保持线性执行语义，认知成本最低。

### 4.2 分流节点的连线约束

- 分流节点后可接“直接流转”连线和“条件流转”连线
- 分流节点后允许存在多条直接流转边
- 分流节点后允许存在多条条件流转边
- 分流后的子链路不允许再汇合

### 4.3 分流节点的执行语义

到达分流节点后，按连线顺序依次检查并执行：

- 直接流转边：无条件执行
- 条件流转边：条件满足时执行

命中的所有边都会继续进入各自子链路，因此一个分流节点可以同时触发多条后续路径。

该语义不是 `if / else if / else`，而是“多路分流 + 多命中派发”。

## 5. 条件流转边设计

### 5.1 条件承载位置

- 判断条件不再配置在分流节点上
- 每条条件流转边单独配置自己的命中条件

这样可以让“路径”和“路径命中条件”绑定，阅读时更直观。

### 5.2 条件配置能力

每条条件流转边支持：

- 多个条件项
- 条件项之间配置逻辑关系：`AND / OR`

第一阶段建议：

- 支持单层条件组合
- 不支持嵌套布尔表达式树

这样既能满足常见业务场景，也能控制实现复杂度。

## 6. 冲突处理策略

由于分流节点可能同时进入多条子链，多个子链路可能修改同一个目标字段或组件状态，因此必须定义冲突策略。

当前建议策略：

- 多个子链路修改同一目标时，按后执行覆盖前执行

这一定义简单、可实现，但会引入一个要求：

- 用户必须能明确看见边顺序
- 调试面板必须能看见覆盖链路

否则会增加排障成本。

## 7. 认知分析

### 7.1 认知优势

该模型相比“条件节点 true/false 分叉”更适合多路分流场景，优势包括：

- 节点职责更清晰：分流节点只负责分流
- 条件与路径绑定，阅读更直观
- 支持超过 2 条分流路径
- 保留树状、单向展开结构，不引入复杂 DAG 合流语义

### 7.2 认知风险

该模型最容易被误解的点在于：

- 用户天然会把“分支”理解为择一路径
- 但此模型中，一个分流节点可能同时进入多条子链路

因此：

- 如果仍命名为“分支节点”，会增加误解概率
- 应明确命名为“分流节点”或“派发节点”

### 7.3 认知结论

该模型不是最天然的传统流程分支认知，但在命名准确、顺序可视、调试充分的前提下，整体是容易理解的。

更准确的用户心智应为：

- 普通节点负责顺序执行
- 分流节点负责把执行流分发到多个河道
- 条件写在河道上
- 命中的河道都会继续流转

## 8. 使用体验分析

### 8.1 使用上的优点

- 比链式 `if/else if/else` 更适合配置多路规则
- 比“trigger 后直接挂多个条件节点”更结构化
- 路径图比并行规则集合更直观

### 8.2 使用上的挑战

- 需要用户理解“多条边可同时命中”
- 需要用户理解“后执行覆盖前执行”
- 如果边顺序展示不明显，用户难以预测最终结果

### 8.3 使用体验结论

该模型在复杂交互规则场景下使用体验较好，但前提是产品必须提供足够的辅助信息：

- 边顺序可视化
- 条件命中结果可视化
- 冲突覆盖 trace 可视化

## 9. 产品设计建议

### 9.1 命名建议

建议正式采用：

- 分流节点

不建议继续使用：

- 分支节点

### 9.2 编辑器约束建议

- 普通节点仅允许 1 条直接流转边
- 分流节点允许多条直接流转边
- 分流节点允许多条条件流转边
- 分流后的链路禁止再汇合

### 9.3 画布呈现建议

- 明确显示边顺序
- 条件流转边展示条件摘要
- 直接流转边展示“直接流转”标识

### 9.4 调试建议

调试面板需至少展示：

- 到达了哪个分流节点
- 哪些边被顺序检查
- 哪些条件流转边命中
- 哪些子链被执行
- 哪些命令产生了覆盖
- 最终哪个结果生效

## 10. 最终结论

分流节点模型是一套合理、自洽的树状执行模型。

它的核心特征是：

- 普通节点单链执行
- 分流节点承载多路分流能力
- 条件写在线上
- 命中的多条子链均可继续执行
- 子链不再汇合
- 冲突按后执行覆盖

从产品角度看，这套模型不是最传统的“条件分支”认知，但在准确命名为“分流节点”后，整体认知和使用体验是可以接受的，并且更适合复杂交互规则场景。
