# 表单结构持久化方案

## 1. 目标与背景

单表单编辑器场景下，前端表单设计器维护的是一份编辑态节点树：

- 前端内部状态包含 `page_root + nodesById`
- `page_root` 仅用于页面标题、说明等页面级信息
- 提交给后端时，前端会过滤掉 `page_root`
- `page_root.props.title` 映射为表单名 `name`
- `page_root.props.description` 映射为表单说明 `description`
- 剩余 `nodesById` 会转换为 JSON，作为 `fields` 字段传给后端

因此，后端不需要处理根节点是否存在的问题，也不以 `page_root` 作为结构校验前提。后端要解决的是：

1. 如何持久化表单头信息与字段树快照
2. 如何为每个字段分配稳定的 `serverId/field_key`
3. 如何支撑后续字段级权限、规则、打印、报表等治理能力
4. 如何控制 JSON 与字段索引表之间的数据同步成本

## 2. 结论

推荐采用“快照 JSON + 字段索引表”的双轨持久化模型，而不是只存 JSON，也不是完全拆成纯关系模型。

结论如下：

1. `fields_json` 作为前端结构保真快照，负责编辑器回显、布局还原、发布版本冻结。
2. 字段索引表作为治理模型，负责字段级权限、规则绑定、打印映射、报表配置等场景。
3. `field_key` 作为后端稳定字段标识，需要写回 `fields_json`，并同步进入索引表。
4. 单体阶段同步采用“事务内保存快照 + 覆盖式重建索引表”的方式，优先保证一致性与实现简单。
5. 当字段量和保存频率明显上升后，再演进为增量同步，而不是一开始就做复杂差量算法。

## 3. 为什么不能只存一份 JSON

只存 `fields_json` 的优点：

- 保存逻辑简单
- 和前端结构天然一致
- 回显与版本快照最完整

但只存 JSON 会带来以下问题：

- 字段级权限难以高效配置和查询
- 规则、打印、报表会反复解析 JSON
- 很难稳定引用“某一个字段”
- 跨版本追踪字段演进困难
- 难以建立数据库层面的唯一性和关联约束

因此，只存 JSON 适合非常轻量的编辑器原型，不适合作为后续可治理的正式方案。

## 4. 为什么也不建议完全只拆字段表

如果完全转成关系表，虽然字段治理会更方便，但会引入新的问题：

- 前端嵌套结构、容器布局、可扩展属性会被强行范式化
- 编辑器保存和回显会变复杂
- 发布时难以精确保留前端原始结构
- 属性扩展会频繁改表或堆砌附表

因此，不建议把 `fields_json` 去掉，而是保留其作为结构快照真相。

## 5. 推荐数据库模型

### 5.1 表单头信息

`form_definition`

建议字段：

- `id`
- `tenant_id`
- `form_code`
- `name`
- `description`
- `status`
- `current_version_id`
- `created_by` `created_at`
- `updated_by` `updated_at`
- `deleted`

职责：

- 承载表单主身份
- 支撑列表查询、筛选、检索
- 保存页面级头信息
- 挂接当前发布版本

说明：

- `name` 来源于前端 `page_root.props.title`
- `description` 来源于前端 `page_root.props.description`
- 不保存 `page_root` 节点本身

### 5.2 草稿快照

`form_draft`

建议字段：

- `id`
- `tenant_id`
- `form_id`
- `fields_json`
- `version`
- `updated_by`
- `updated_at`

职责：

- 保存当前可编辑字段树
- 作为编辑器再次打开时的草稿加载来源
- 保存已写回 `field_key/serverId` 的结构快照

约束建议：

- `form_id` 唯一索引
- `version` 用于乐观锁

### 5.3 发布快照

`form_version`

建议字段：

- `id`
- `tenant_id`
- `form_id`
- `version_no`
- `fields_json`
- `published_by`
- `published_at`

职责：

- 保存发布时不可变快照
- 运行时渲染、记录校验、规则执行统一基于发布版

约束建议：

- `(form_id, version_no)` 唯一索引

### 5.4 草稿字段索引表

`form_field`

建议字段：

- `id`
- `tenant_id`
- `form_id`
- `field_key`
- `field_code`
- `field_name`
- `node_type`
- `component_type`
- `parent_field_key`
- `sort_no`
- `status`
- `created_at`
- `updated_at`

职责：

- 作为草稿态字段治理索引
- 支撑字段级权限配置
- 支撑规则绑定、打印字段选择、报表字段选择等能力

说明：

- 该表是索引表，不替代 `fields_json`
- 只保存治理需要的最小字段集，不保存全部 `props`

### 5.5 发布版字段索引表

`form_version_field`

建议字段：

- `id`
- `tenant_id`
- `form_version_id`
- `form_id`
- `field_key`
- `field_code`
- `field_name`
- `node_type`
- `component_type`
- `parent_field_key`
- `sort_no`
- `created_at`

职责：

- 固化发布版字段索引
- 让权限、规则、打印、报表绑定到明确版本

## 6. field_key / serverId 设计原则

### 6.1 角色定义

建议区分两类标识：

- 前端 `id`
  - 用于编辑器内部节点引用
  - 可以是临时值
  - 在复制、拖拽、重建结构时可能变化

- 后端 `field_key`，即前端所说的 `serverId`
  - 用于字段的稳定业务标识
  - 由后端生成并长期保持稳定
  - 用于权限、规则、打印、报表、跨版本追踪

### 6.2 生成规则

建议规则：

1. 前端新增字段时，允许 `field_key/serverId` 为空
2. 后端第一次保存草稿时，为缺失的字段生成 `field_key`
3. 后端将生成后的 `field_key` 写回 `fields_json`
4. 保存结果返回前端后，前端后续提交必须原样带回
5. 已存在的 `field_key` 不允许在普通编辑中被重置

### 6.3 是否需要每个字段单独存一份 serverId

需要，但不是指“只为了 `serverId` 就把所有字段完全拆表”。

更准确的做法是：

- `field_key` 写入 `fields_json`
- `field_key` 同时落入 `form_field` / `form_version_field`

这样既保证前端结构完整，又保证后端可以按字段维度治理。

## 7. 后端如何做组件关系合法性校验

即使前端已经过滤掉 `page_root`，后端仍然需要校验字段子图是否合法。校验重点不再是根节点存在性，而是节点关系和组件约束。

建议校验项如下：

### 7.1 结构完整性

- 每个节点 `id` 唯一
- 每个节点 `field_key` 在表单内唯一
- `childrenIds` 中的节点必须存在
- 子节点的 `parentId` 必须回指父节点
- 顶层节点集合必须明确，可通过 `parentId = null` 或单独的 `rootNodeIds` 表达

### 7.2 关系合法性

- `field` 节点不能拥有子节点
- 只有 `container` 节点可以承载子节点
- 不允许循环引用
- 不允许无法从顶层节点遍历到的孤儿节点

### 7.3 组件约束

- 输入类组件必须有 `label`
- `radio/checkbox/select` 必须有 `options`
- 布局类字段如 `span` 必须在允许范围内

### 7.4 发布前校验

- 所有节点必须可达
- 所有必填字段属性合法
- 所有字段稳定标识 `field_key` 已补齐

## 8. 如何权衡同步负荷与索引表收益

这是本方案的核心权衡点。

### 8.1 索引表带来的便利

引入字段索引表后，可以显著提升以下能力：

- 字段级权限配置
- 规则绑定
- 打印模板字段选择
- 报表字段配置
- 跨版本字段追踪
- SQL 级筛选、检索、关联

如果后续明确要做字段级权限，这些收益通常足以覆盖同步成本。

### 8.2 同步带来的负担

同步成本主要体现在：

- 保存草稿时需要同时维护 `fields_json` 和 `form_field`
- 发布时需要同时维护 `form_version.fields_json` 和 `form_version_field`
- 需要保证 `field_key` 在两套结构中一致

### 8.3 推荐权衡策略

推荐接受这份同步成本，但控制同步范围：

1. `fields_json` 仍为结构主事实源
2. 索引表只存治理所需最小字段集
3. 不把全部 `props` 范式化拆表
4. 不在查询时动态重建索引表
5. 只在保存草稿和发布两个动作上做同步

这意味着：

- 前端结构仍然简单自然
- 后端治理能力明显增强
- 同步复杂度被限定在可控范围

## 9. 推荐同步策略

### 9.1 草稿保存

在单体阶段，推荐使用“事务内覆盖式重建”：

1. 接收前端提交的 `name`、`description`、`fields`
2. 校验字段图合法性
3. 为缺失的节点补齐 `field_key`
4. 将补齐后的结果写回 `fields_json`
5. 更新 `form_definition.name/description`
6. 更新 `form_draft.fields_json/version`
7. 删除该表单旧的 `form_field`
8. 从 `fields_json` 重新解析并插入新的 `form_field`
9. 提交事务

优点：

- 实现简单
- 一致性最容易保证
- 对中小型表单足够稳定

缺点：

- 每次保存都有一定写放大

### 9.2 发布

发布时同样建议在一个事务中完成：

1. 读取草稿快照
2. 写入 `form_version`
3. 从草稿解析生成 `form_version_field`
4. 更新 `form_definition.current_version_id/status`
5. 提交事务

### 9.3 为什么先不用增量同步

增量同步虽然写入更轻，但复杂度明显更高：

- 要比较新旧 JSON 差异
- 要识别新增、删除、重命名、移动
- 要处理父子关系和排序变化

因此，在单表单编辑器阶段，不建议一开始就引入差量同步。只有当字段量、保存频率和并发量明显增长时，再考虑演进为按 `field_key` 的增量同步。

## 10. 权限模型建议

若要支持字段级权限，建议增加独立权限策略表，例如：

`field_permission_policy`

建议字段：

- `id`
- `tenant_id`
- `form_id` 或 `form_version_id`
- `field_key`
- `subject_type`
- `subject_id`
- `perm_code`
- `created_at`
- `updated_at`

其中：

- `subject_type` 可取 `USER/ROLE/DEPARTMENT`
- `perm_code` 可取 `VIEW/EDIT/HIDDEN/MASK/REQUIRED`

建议优先面向发布版生效，即优先使用 `form_version_id + field_key` 进行权限约束，避免草稿频繁变动带来的权限漂移。

## 11. 实施建议

### 11.1 当前阶段

推荐立即采用：

- `form_definition`
- `form_draft.fields_json`
- `form_version.fields_json`
- `form_field`
- `form_version_field`

并采用“事务内覆盖式重建索引表”的同步策略。

### 11.2 后续演进

在以下条件出现后，再考虑升级为增量同步：

- 单表字段数量明显变大
- 草稿保存频率高
- 表单设计多人协作并发高
- 保存耗时成为明显瓶颈

## 12. 最终建议

本方案的最终建议是：

1. 保留 `fields_json`，作为表单结构快照真相
2. 新增字段索引表，作为字段治理与权限配置基础
3. `field_key/serverId` 必须写回 JSON，并同步进入索引表
4. 当前阶段优先保证一致性与简单性，采用事务内覆盖式重建
5. 不为追求早期优化而过早引入复杂增量同步算法

这套设计既能满足当前单表单编辑器的落地效率，也为后续字段级权限、规则、打印、报表和版本追踪保留了稳定基础。
