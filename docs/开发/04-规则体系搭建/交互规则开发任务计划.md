## 3. 本阶段统一技术与实现约束

### 3.1 范围约束

| 约束 | 说明 |
|---|---|
| 当前表单边界 | 交互规则只能影响当前表单的主表、明细表、关联选择和页面状态 |
| 关键规则重放 | 提交前必须由后端重放关键交互规则，前端结果不能作为最终裁决 |
| 图编排与标准化分离 | 前端做规则图编辑与预编译，后端做最终标准化与发布版管理 |
| 运行态写入口唯一 | 事实数据和派生状态变更统一通过命令协议落到运行时状态 |
| 明细行定位 | 一律使用 `rowId`，禁止用 `rowIndex` 作为稳定定位键 |

### 3.2 节点与命令约束

| 维度 | 当前阶段约束 |
|---|---|
| 执行节点 | 只支持 `trigger`、`condition`、`query`、`transform`、`context`、`command`、`notice` |
| 命令类型 | 只支持 `setValue`、`clearValue`、`setVisible`、`setReadonly`、`setRequired`、`setOptions`、`setFilter`、`appendRow`、`updateRow`、`replaceTable`、`showMessage`、`setValidationError` |
| 规则事件 | 只支持 `FIELD_CHANGE_MAIN`、`FIELD_CHANGE_DETAIL`、`DETAIL_ROW_ADDED`、`DETAIL_ROW_REMOVED`、`RELATION_OPEN`、`RELATION_SELECTED`、`FORM_INIT`、`FORM_SUBMIT_BEFORE` |
| 组件类型 | 优先支持基础输入类、选择类、关联选择、明细表、容器 |

### 3.3 接口约束

| 能力 | 要求 |
|---|---|
| 编辑态接口 | 必须支持草稿加载、草稿保存、发布前校验、发布、已发布版本加载 |
| 预览调试 | 必须支持草稿规则的预览执行和节点级结果返回 |
| 运行态接口 | 必须支持按表单版本加载已发布交互规则 |
| 查询接口 | 必须支持字段选择、过滤、排序、分页、权限过滤 |
| 提交回传 | 必须回传纠偏后的 `mainData/detailTables/validationErrors/ruleDiagnostics` |

## 5. Sprint 任务分解（S1-S6）

### 5.1 Sprint 1：规则基础骨架

**里程碑目标**

管理员可以从表单编辑器进入“交互规则”页，看到规则列表和空白规则编辑器，可以新建规则草稿并保存。

**业务验收场景**

1. 从表单编辑器进入交互规则入口
2. 新建一条规则草稿
3. 保存草稿成功
4. 再次进入时可回显草稿基础信息

| 类别 | 任务 | 输入 | 输出 | 前置依赖 | DoD |
|---|---|---|---|---|---|
| 开发 | 交互规则入口与路由接入 | 表单编辑器现有骨架 | 交互规则入口、页面路由 | 无 | 管理员可从表单编辑器进入交互规则页面 |
| 开发 | 规则列表页与空态页骨架 | 交互规则编辑态设计 | 规则列表、空白态、基础操作区 | 入口接入 | 页面可展示当前表单的规则列表空态 |
| 开发 | 规则元信息模型与草稿状态 | 交互规则前端设计中的 `interactionRuleDraftSlice` | 规则 meta store、保存状态、错误状态 | 无 | 规则名称、编码、优先级、事件类型等可编辑 |
| 开发 | 规则草稿后端基础表结构与仓储骨架 | 后端规则表设计 | `rule_definition/rule_draft` 基础落库能力 | 无 | 可创建和更新交互规则草稿 |
| 开发 | 草稿保存/加载接口第一版 | 后端补充接口约束 | 草稿加载接口、草稿保存接口 | 表结构完成 | 前端可保存和加载规则草稿元信息 |
| 联调 | 表单维度规则草稿闭环 | 前端页面 + 后端草稿接口 | 创建草稿 -> 保存 -> 再加载闭环 | 开发任务完成 | 草稿数据完整回显，无重复创建问题 |
| 测试 | 规则入口与草稿冒烟 | 页面、接口 | 冒烟用例和缺陷记录 | 联调完成 | 无阻塞缺陷 |
| 发布前检查 | Sprint 演示评审 | 演示脚本 | 评审记录 | 全部任务完成 | 可完整演示“进入规则页-新建规则-保存草稿-重新打开回显” |

**补充任务细节**

- 前端规则页先只实现三块：规则列表、规则基础信息区、画布占位
- 规则草稿保存请求至少包含：`ruleCode`、`ruleName`、`eventType`、`priority`、`graph_json={}`、`compiled_json={}`
- 后端此 sprint 不要求最终标准化，只要求能保存草稿基础结构
- 规则编码可先由后端生成，也可前端临时生成后由后端回写正式编码，但需要约定唯一策略

### 5.2 Sprint 2：规则图编辑与发布闭环

**里程碑目标**

管理员可以通过规则画布拖入基础节点、配置连线、保存草稿、做发布前校验并发布规则；发布后可按表单版本加载发布版规则。

**业务验收场景**

1. 新建一条规则
2. 配置 `trigger -> condition -> command`
3. 保存草稿
4. 触发发布前校验
5. 发布成功
6. 可查看已发布版本

| 类别 | 任务 | 输入 | 输出 | 前置依赖 | DoD |
|---|---|---|---|---|---|
| 开发 | 规则图模型与编辑态 store 落地 | `interactionRuleGraphSlice` 设计 | `nodes/edges/diagnostics/references` 管理能力 | Sprint 1 | 图节点和连线可增删改 |
| 开发 | 节点面板与属性面板第一版 | 执行节点协议设计 | `trigger/condition/query/transform/command/context/notice` 基础配置面板 | 图模型 | 可编辑节点基础参数 |
| 开发 | 规则画布第一版 | 交互规则编辑器设计 | 节点拖入、选中、连线、删除 | 图模型 | 规则图可视化编排可用 |
| 开发 | 规则预编译器第一版 | 执行节点协议、命令协议 | `graph_json -> compiled_json + diagnostics + references` | 节点配置可用 | 可识别断链、非法字段、缺失配置 |
| 开发 | 后端规则发布模型与版本表落地 | `rule_version/rule_trigger_binding/rule_reference_index` 设计 | 发布版存储与触发器索引 | Sprint 1 | 支持规则发布和版本记录 |
| 开发 | 发布前校验接口 | 后端补充约束 | 返回诊断、引用问题、配置错误 | 预编译器 | 前后端联合校验结果一致 |
| 开发 | 发布接口与发布版加载接口 | 后端补充约束 | 发布、加载已发布规则接口 | 版本模型 | 按表单版本可加载已发布规则 |
| 联调 | 编辑-校验-发布闭环 | 前端规则图 + 后端版本接口 | 草稿规则可发布并可加载已发布版本 | 开发任务完成 | 发布态和草稿态隔离正确 |
| 测试 | 规则图与发布专项测试 | 规则图场景 | 连线合法性、节点必填、发布阻断报告 | 联调完成 | 关键非法场景能被阻断 |
| 发布前检查 | Sprint 演示评审 | 演示脚本 | 评审记录 | 全部任务完成 | 可演示“创建规则图-校验-发布-查看发布版” |

**补充任务细节**

- 当前 sprint 节点配置先不追求全部高级参数，重点保证基础配置完整可回显
- `references` 必须至少提取：字段引用、明细表引用、事件引用、触发目标引用
- 发布时必须落 `compiled_json`、`normalized_json`、`dependency_json` 的占位或初版结构
- 允许后端在发布时重新规范化前端编译结果，前端不是标准化权威

### 5.3 Sprint 3：运行时基础链路

**里程碑目标**

填报页可加载已发布交互规则，字段变化可触发规则执行，支持最简单的字段显隐、只读、必填、赋值类联动。

**业务验收场景**

1. 页面加载已发布规则
2. 主表字段值变化
3. 命中规则
4. 受影响字段隐藏/显示或只读/必填变化
5. 页面局部刷新，无整页重绘感

| 类别 | 任务 | 输入 | 输出 | 前置依赖 | DoD |
|---|---|---|---|---|---|
| 开发 | 运行态规则加载器 | 发布版规则接口 | 按表单版本加载规则并缓存 | Sprint 2 | 进入填报页可拿到规则配置 |
| 开发 | `interactionRuntimeSlice` 与 `interactionEngineSlice` 落地 | 前端运行态设计 | 事实数据、组件状态、事件队列、轨迹管理 | 无 | 运行态 store 可初始化 |
| 开发 | `RuleExecutionContext` 与上下文构建器 | 执行节点协议 | 单次执行上下文构建能力 | 运行态 store | 事件触发后可正确读取主表/明细数据 |
| 开发 | 事件总线与运行时桥接 | `RuntimeEventBridge` 设计 | 字段变化转标准事件 | 运行态 store | 字段变化可入队 |
| 开发 | 节点执行器基础版 | `trigger/condition/context/command/notice` | 简单规则顺序执行能力 | 上下文构建器 | 可执行字段显隐、只读、必填、简单赋值 |
| 开发 | 命令分发器第一版 | 命令协议设计 | `setVisible/setReadonly/setRequired/setValue/clearValue` 落地 | 节点执行器 | 命令可稳定写入运行态状态 |
| 开发 | 运行时模型对象第一版 | 运行时模型对象设计 | 基础字段模型、选择类模型、关联选择模型雏形 | 命令分发器 | 组件状态更新逻辑内聚 |
| 联调 | 简单联动闭环 | 规则图 -> 运行时执行 -> 页面变化 | 表单字段联动完整跑通 | 开发任务完成 | 基础联动规则在编辑、发布、填报三端一致 |
| 测试 | 运行时基础专项测试 | 字段联动场景 | 字段显隐/只读/必填/赋值测试报告 | 联调完成 | 响应及时、结果准确 |
| 发布前检查 | Sprint 演示评审 | 演示脚本 | 评审记录 | 全部任务完成 | 可演示“字段变化 -> 页面联动更新” |

**补充任务细节**

- 本 sprint 只要求支持主表 -> 主表 的基础联动
- UI 变化必须有可追踪的规则执行轨迹和命令记录
- 运行时模型对象采用“单次创建处理命令 -> 输出快照”的方案，不引入常驻组件树
- 规则执行失败时至少支持两种策略：中断并提示、跳过并记录诊断

### 5.4 Sprint 4：关联选择与明细联动

**里程碑目标**

跑通两个核心复杂场景：

1. 点击关联选择，弹出候选记录并完成主表/明细行回填  
2. 主表驱动明细、明细汇总主表

**业务验收场景**

1. 打开关联选择，看到目标表单记录
2. 选中记录后回填主表字段
3. 明细行中的关联选择可回填当前行
4. 主表字段变化可刷新明细列状态或候选项
5. 明细字段变化可汇总到主表

| 类别 | 任务 | 输入 | 输出 | 前置依赖 | DoD |
|---|---|---|---|---|---|
| 开发 | `query` 节点执行器 | 执行节点协议、后端统一查询约束 | 查询当前表单、明细行、关联表记录 | Sprint 3 | 可根据配置返回结构化查询结果 |
| 开发 | `transform` 节点执行器 | 执行节点协议 | 字段映射、过滤、排序、聚合、选项映射 | query 节点 | 可支撑候选项转换和汇总计算 |
| 开发 | `setOptions/setFilter/appendRow/updateRow/replaceTable` 命令落地 | 命令协议 | 关联选择、明细批量更新相关命令 | 命令分发器基础版 | 组件状态和明细数据可正确更新 |
| 开发 | 关联选择弹层与上下文承载 | 交互规则前端设计 | 关联选择弹层上下文、候选项展示、确认回填 | 运行态基础链路 | 主表和明细行均可使用统一弹层 |
| 开发 | 后端统一规则查询接口 | 后端补充约束 | 规则查询网关 DTO、过滤、排序、分页能力 | 规则中心基础接口 | 可承接前端 `query` 节点 |
| 开发 | 明细表相关运行时支持 | rowId、detailTable 命令目标 | 明细行定位、整表更新、行级事件 | 运行态基础链路 | 主表 -> 明细、明细 -> 主表 能稳定执行 |
| 联调 | 关联选择闭环 | 规则 -> 查询 -> 候选项 -> 选中 -> 回填 | 主表和明细行关联选择均可跑通 | 开发任务完成 | 候选项正确、回填准确、不串行 |
| 联调 | 明细联动闭环 | 主表驱动明细、明细汇总主表 | 规则在复杂作用域下稳定执行 | 开发任务完成 | 不同行互不串扰，汇总准确 |
| 测试 | 复杂场景专项测试 | 关联选择、明细联动场景 | 测试报告 | 联调完成 | 关键复杂场景通过 |
| 发布前检查 | Sprint 演示评审 | 演示脚本 | 评审记录 | 全部任务完成 | 可演示“关联选择候选项加载、回填、明细汇总” |

**补充任务细节**

- 关联选择候选项加载规则必须基于 `RELATION_OPEN` 和 `RELATION_SELECTED` 两类事件打通
- 明细表运行态必须统一用 `rowId`，不得再基于 `rowIndex` 做稳定定位
- 关联选择的组件专属状态挂到字段自身状态对象，不再外挂单独状态源
- 查询接口至少要支持基于前端 `fieldSelection/filters/sorters/pageSize` 的通用 DTO

### 5.5 Sprint 5：提交前预校验与后端重放

**里程碑目标**

提交前交互规则能阻断非法输入，后端可重放关键规则并返回最终纠偏结果，前后端执行结果可对齐。

**业务验收场景**

1. 用户点击提交
2. 前端触发 `FORM_SUBMIT_BEFORE`
3. 命中预校验规则并给出错误定位
4. 前端通过后提交事实数据
5. 后端重放关键规则
6. 若后端纠偏或校验失败，可将最终结果回传页面

| 类别 | 任务 | 输入 | 输出 | 前置依赖 | DoD |
|---|---|---|---|---|---|
| 开发 | `FORM_SUBMIT_BEFORE` 事件链路 | 运行态事件总线 | 提交前规则执行能力 | Sprint 3/4 | 点击提交前可先执行规则 |
| 开发 | `setValidationError/clearValidationError/showMessage` 命令落地 | 命令协议 | 字段级错误和提示信息统一处理 | 命令分发器 | 可在页面上稳定定位错误 |

**补充任务细节**

- 后端不需要回传 UI 命令本身，但必须回传能映射到前端运行态的等价结果
- 提交场景至少要覆盖：必填校验、简单计算一致性、唯一性示例、隐藏字段清理策略
- 前端提交时只提交事实数据，不提交派生状态
- 纠偏回传后应有明确的“后端已修正结果”处理策略，避免用户误以为仍是本地结果

### 5.6 Sprint 6：调试、治理与稳定性

**里程碑目标**

**业务验收场景**

1. 编辑态模拟执行一条规则
2. 查看节点执行顺序和输入输出摘要
3. 运行态可看到基础规则轨迹

## 9. 风险与缓解

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| 规则范围膨胀 | 第一阶段被业务规则侵入，交付失控 | 严格限定当前表单边界，不做跨表事务 |
| 接口契约滞后 | 前端规则图和后端规则中心无法联调 | Sprint 1-2 优先明确草稿、发布、校验接口 |
| 运行态复杂度失控 | 命令桥和组件状态不断膨胀 | 坚持命令协议、运行时模型对象、节点协议三层分离 |
| 明细场景不稳定 | rowIndex 导致回填和汇总错位 | 全链路统一 `rowId/rowVersion` |
| 前后端结果不一致 | 页面展示与提交结果不同 | Sprint 5 强制建立后端关键规则重放和结果回传 |
| 调试困难 | 线上问题难以定位 | Sprint 6 建立规则ID/节点ID/执行ID 全链路日志 |

## 10. 推荐实施顺序结论

本阶段不应按前后端分仓式拆任务，而应按业务闭环拆：

1. 先打通“规则可编辑、可保存、可发布”
2. 再打通“规则可加载、可执行、可改变页面”
3. 然后补齐“复杂作用域场景：关联选择和明细联动”
4. 最后补齐“提交前预校验、后端重放、调试定位”

这样每个 sprint 都有可直接验收的小里程碑，也能保证团队始终围绕“业务能跑通”推进，而不是陷入纯技术组件堆叠。
