# 元数据与填报数据一致性策略

## 1. 目标

本文档用于明确“单表单填报”场景下，表单元数据与填报数据之间的一致性处理策略，重点回答以下问题：

1. 表单结构发生变更后，如何保证新旧填报数据都能正确解释
2. 历史记录是否需要跟随最新表单结构变化
3. 如何在运行态、查询态、报表态处理多版本结构带来的差异

本文档适用于：

- 单表单填报
- 后续多表单扩展
- 历史数据回看
- 导出、报表、审计等依赖填报数据的场景

## 2. 核心原则

本方案采用以下三个核心原则：

1. 元数据必须版本化
2. 填报数据必须绑定元数据版本
3. 历史记录始终按提交时版本解释，不按最新版本回放

一句话总结：

**元数据版本化，数据永远绑定版本，不追最新结构。**

## 3. 一致性总策略

### 3.1 表单结构必须版本化

每次表单发布时，必须生成新的 `form_version`。

`form_version` 保存：

- 表单头信息快照
- 字段结构快照
- 发布时字段索引快照

建议以以下内容作为发布版事实源：

- `form_version.fields_json`
- `form_version_field`

说明：

- 编辑器草稿不作为填报运行时事实源
- 填报、查询、提交、导出均只能依赖发布版结构

### 3.2 记录必须绑定结构版本

每一条填报记录都必须保存其所属的：

- `form_id`
- `form_version_id`

必要时还可冗余：

- `form_version_no`

这意味着：

- 即使同一个 `form_id` 后续又发布了新版本
- 历史记录仍然知道自己是基于哪一版结构创建和提交的

### 3.3 历史记录不追随最新结构

查看历史数据时，后端必须：

1. 读取记录绑定的 `form_version_id`
2. 加载对应 `form_version` 快照
3. 使用该版本的 `fields_json` 或 `form_version_field` 解释 `record_data`

不允许：

- 用最新表单结构解释旧记录
- 用草稿结构解释已提交记录
- 在查询时临时按最新字段标题覆盖旧版本含义

## 4. 推荐数据模型

### 4.1 元数据

推荐使用以下结构：

- `form_definition`
  - 表单逻辑身份
  - 当前发布指针

- `form_version`
  - 发布版结构快照
  - 字段树事实源

- `form_version_field`
  - 发布版字段索引
  - 供权限、规则、报表、打印等能力稳定引用

### 4.2 填报数据

推荐使用以下结构：

- `record_main`
  - `id`
  - `form_id`
  - `form_version_id`
  - `status`
  - `created_by`
  - `submitted_at`

- `record_data`
  - `record_id`
  - `data_json`
  - `search_json`

### 4.3 解释关系

查询一条记录时，应采用以下链路：

1. `record_main.form_version_id`
2. `form_version.fields_json`
3. `record_data.data_json`

也就是说：

- `form_version` 负责告诉系统“这条记录应该如何被解释”
- `record_data` 负责保存“用户当时实际提交了什么值”

## 5. 表单结构变更时如何处理历史数据

### 5.1 新增字段

处理方式：

- 老记录中自然不存在该字段
- 查询历史记录时显示为空即可
- 不需要回填历史数据

影响范围：

- 仅影响新版本之后的新记录

### 5.2 删除字段

处理方式：

- 老记录中已有该字段值的，仍按旧版本结构展示
- 新版本中不再出现该字段

影响范围：

- 不删除历史记录中的原值
- 不修改历史版本中的结构快照

### 5.3 修改字段标题

处理方式：

- 历史记录按旧版本标题解释
- 新记录按新版本标题解释

注意：

- 不应用最新标题去覆盖历史记录展示
- 否则会造成历史语义漂移

### 5.4 修改字段类型

这是高风险变更。

例如：

- `input -> select`
- `number -> date`
- `single-select -> multi-select`

处理方式：

- 不修改历史记录
- 历史记录继续按旧版本类型解释
- 新版本记录按新类型校验和展示

原因：

- 同一份历史值在新类型下可能完全无法正确解释

### 5.5 调整字段层级或布局

处理方式：

- 历史记录仍按旧版本布局与结构解释
- 新版本记录按新布局解释

说明：

- 布局变化属于结构变化的一部分，也应版本隔离

## 6. 为什么历史数据不能跟着最新结构走

如果历史数据跟随最新结构解释，会带来以下问题：

1. 已删除字段会在历史数据中丢失语义
2. 字段类型变更后旧值可能不可解释
3. 标题变化会导致历史业务含义漂移
4. 审计追溯无法还原“当时用户看到的结构”
5. 报表、导出、审批回放会产生不一致结果

因此：

**历史数据必须冻结在其提交时对应的结构版本上。**

## 7. field_key 的作用

为了更好地处理跨版本结构演进，建议每个字段保留稳定的 `field_key/serverId`。

### 7.1 field_key 的职责

`field_key` 不是为了让旧记录自动适配新结构，而是为了：

- 判断两个版本中的字段是否是同一个业务字段
- 支撑权限配置继承
- 支撑规则、打印、报表字段绑定
- 支撑版本差异分析

### 7.2 field_key 的使用原则

1. 同一个业务字段跨版本尽量保持同一个 `field_key`
2. 标题、位置、布局变更时不应重新生成 `field_key`
3. 新增字段才分配新的 `field_key`
4. 删除字段后旧版本中的 `field_key` 仍然保留在历史快照中

## 8. 运行态一致性处理

### 8.1 新建填报

新建记录时：

1. 后端读取当前有效的 `form_version`
2. 将该版本号和版本 ID 绑定到记录
3. 后续该记录始终使用该版本解释

### 8.2 暂存草稿

若记录支持草稿：

- 草稿记录也应绑定创建时使用的 `form_version_id`
- 不建议在草稿未提交时自动切换到新发布版本

否则可能出现：

- 用户保存草稿时看到 A 结构
- 继续编辑时系统变成 B 结构
- 导致字段丢失或校验规则漂移

### 8.3 提交校验

提交时：

1. 后端读取记录绑定的 `form_version_id`
2. 按该版本结构进行字段校验
3. 不以当前最新版本校验

这样才能保证：

- 草稿与提交过程的一致性
- 历史填报行为的可解释性

## 9. 报表与跨版本统一口径处理

历史记录不跟随最新结构，并不意味着无法做跨版本统一分析。

正确做法是：

- 交易存储保持版本隔离
- 查询分析层做字段映射或投影归一

### 9.1 推荐做法

推荐新增以下能力之一：

1. 报表投影表
2. 跨版本字段映射规则
3. 基于 `field_key` 的统一视图

### 9.2 原则

不建议：

- 直接修改历史记录原始值
- 直接覆盖历史版本结构

建议：

- 保留原始记录
- 保留原始版本快照
- 新建派生投影或映射结果

## 10. 什么时候才需要迁移历史数据

大多数情况下，不需要迁移历史记录本身。

只有在以下场景，才考虑做专门迁移：

1. 法规要求统一历史口径
2. 报表系统必须使用统一字段模型
3. 早期结构设计存在严重错误且必须修复

即使需要迁移，也应遵循以下原则：

1. 原始记录不可覆盖删除
2. 迁移过程可追踪
3. 迁移规则可审计
4. 迁移结果与原始数据分层存储

也就是说：

- 迁移应生成新投影、新结果或新批次
- 不应直接篡改原始交易事实

## 11. 推荐落地规则清单

建议在实现中明确以下规则：

1. 每次发布必须生成新的 `form_version`
2. 每条记录必须保存 `form_version_id`
3. 记录查询必须按绑定版本解释
4. 提交校验必须按绑定版本执行
5. 历史记录不按最新结构回放
6. 字段稳定标识 `field_key` 必须跨版本尽量保持稳定
7. 跨版本统一分析应通过映射或投影解决，而不是修改交易记录

## 12. 最终结论

元数据与填报数据之间的一致性，最关键的不是“让所有数据永远跟最新结构一致”，而是：

**让每条记录永远与它创建/提交时对应的元数据版本保持一致。**

因此推荐的最终策略是：

1. 元数据版本化
2. 数据绑定版本
3. 历史数据按历史版本解释
4. 结构变更不直接改历史记录
5. 跨版本统一口径通过映射和投影解决

这套策略既能保证历史数据可追溯、可解释，也能支持后续结构持续演进而不破坏已沉淀的数据资产。
