# 明细表相关命令设计

## 1. 背景

在交互规则中，明细表相关操作与主表字段命令有明显差异：

- 明细表存在“整表”“多行”“单行”“单元格”四个层级
- 主表事件也可能驱动明细表更新
- 行内事件既可能更新当前行，也可能批量影响整张明细表

如果继续沿用主表字段命令的建模方式，会出现两个问题：

- 配置者必须理解 `rowId`、当前行上下文等内部概念，认知负担较高
- 主表触发时缺少“当前行”，导致很多业务场景难以表达

因此，明细表命令需要单独设计。

## 2. 设计目标

明细表相关命令需要满足以下目标：

- 支持主表事件驱动明细表更新
- 支持明细行事件驱动当前行或多行更新
- 尽量避免让配置者直接操作 `rowId`
- 命令配置方式与查询节点尽量一致，降低学习成本
- 让“单字段更新”和“整表更新”各自职责清晰

## 3. 命令分类

明细表相关命令分为三类：

### 3.1 追加明细行

作用：

- 向目标明细表新增一行或多行数据

典型场景：

- 主表字段变化后，从外部表单查询记录并追加到当前明细表
- 关联选择完成后，将关联记录明细批量带入当前明细表

### 3.2 更新明细行

作用：

- 对目标明细表做条件更新
- 满足筛选条件的所有行都会被更新

典型场景：

- 主表字段变化后，把某类明细行的价格统一重算
- 明细行内某字段变化后，批量刷新同一明细表中满足条件的其他行

### 3.3 替换明细表

作用：

- 用新的整表数据直接替换当前明细表

典型场景：

- 根据主表字段重建整张明细表
- 导入模板后整表覆盖

## 4. 更新明细行的产品策略

### 4.1 不采用显式 rowId 配置

不推荐将 `updateRow` 设计成必须显式传入 `rowId` 的模式。

原因：

- `rowId` 更偏运行时内部标识，不符合业务配置者心智
- 主表事件触发时通常没有“当前行”，需要先额外计算目标 `rowId`
- 配置链路会变成“先求 rowId，再更新行”，使用成本高

### 4.2 采用条件更新模型

`更新明细行` 应设计成“针对整张明细表的条件更新命令”。

其核心模型类似：

- 先选择目标明细表
- 再配置筛选条件
- 命中筛选条件的行即为要被更新的行
- 对命中行执行字段写入

这更接近配置者对业务的自然理解，也更接近 SQL 中的：

`update detail_table set ... where ...`

## 5. 更新明细行的配置结构

### 5.1 基础配置

- 目标明细表
- 筛选条件
- 更新字段列表

### 5.2 筛选条件

筛选条件的配置方式应与查询节点保持一致。

建议直接复用查询节点的条件结构：

- 来源字段
- 运算符
- 固定值 / 变量值
- 多条件 AND / OR

这样做的好处：

- 用户不用学习两套条件语法
- 编辑器可以复用已有筛选条件组件
- 编译与运行时协议更统一

### 5.3 字段更新项

每个更新项包含：

- 目标字段
- 值来源模式
  - 固定值
  - 变量值
- 字面量值 / 变量路径

示例：

- `价格 = temp.price`
- `折扣 = 0.9`
- `状态 = "INVALID"`

## 6. 使用边界

### 6.1 主表事件驱动明细表更新

支持。

示例：

- 主表“客户类型”变化
- 更新明细表中所有“商品分类=办公用品”的行
- 将其折扣字段统一改写

此时不需要“当前行”概念，只要筛选条件能命中目标行即可。

### 6.2 行内事件驱动当前行更新

对于“当前行某字段变化 -> 更新当前行另一字段”这类简单联动，不建议强制使用“更新明细行”。

更推荐继续使用：

- `设置值`

原因：

- 配置更轻
- 语义更直接
- 不需要额外配置筛选条件

### 6.3 行内事件驱动多行更新

支持。

此时 `更新明细行` 仍然面向整张明细表，只是筛选条件里可以使用当前事件上下文。

例如：

- 当前行“商品编码”变化
- 更新同一明细表中所有“商品编码相同”的行的价格字段

## 7. 推荐的命令职责划分

建议在产品上明确以下边界：

- `设置值`
  - 面向单字段
  - 常用于当前上下文内联动

- `追加明细行`
  - 面向整张明细表新增

- `更新明细行`
  - 面向整张明细表按条件批量更新

- `替换明细表`
  - 面向整表重建

这样可以减少命令语义重叠，提升可理解性。

## 8. 易用性判断

相较以下两种方案，当前策略更优：

### 8.1 相比显式 rowId 模式

更易用。

原因：

- 用户不需要理解运行时内部行标识
- 不需要额外先求 `rowId`
- 更符合“筛出要改的行”这种业务表述

### 8.2 相比 replaceTable 整表替换

更易用。

原因：

- 不需要构造整表数据
- 只更新命中的行
- 更适合局部更新场景

## 9. 结论

明细表相关命令建议按以下产品策略落地：

- `更新明细行` 采用“条件更新整张明细表”的模型
- 不要求配置者显式传入 `rowId`
- 筛选条件与查询节点保持一致
- 更新项按字段配置，支持固定值和变量值
- 主表触发、行内触发都统一使用这套模型
- 行内简单单字段更新仍优先使用 `设置值`

这套策略在产品上是合理的，也比 `rowIdFrom` 方案更符合用户认知，整体使用体验更优。
