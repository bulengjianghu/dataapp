# 文档管理规范

## 1. 目的

本文档用于统一本仓库 `docs` 目录下的文档管理方式，解决当前文档数量逐步增加后可能出现的以下问题：

- 文档角色边界不清，需求、设计、开发计划内容相互混杂
- 目录层级和命名方式不统一，新增文档时难以快速判断应放在哪里
- 同一阶段缺少总览、主文档与补充文档的区分，阅读路径不稳定
- 文档链接、状态、版本缺少统一约束，协作中容易失效

目标是让团队在 AI 协作、人工评审、研发落地三类场景中，都能快速找到“当前应以哪份文档为准”。

## 2. 当前现状评估

## 2.1 当前结构的优点

当前 `docs` 目录已经具备较好的基础结构，主要优点如下：

- 已按 `需求 / 设计 / 开发` 三层组织，符合从“为什么做”到“怎么做”再到“怎么落地”的协作链路
- 主要能力域已按阶段编号拆分，例如 `01-单表单编辑器`、`02-单表单填报`、`03-多表单扩展`
- 大部分核心文档已经具备较完整的二维表结构，便于 AI 和人工快速抽取信息
- 部分设计文档已经形成“总设计 + 专题设计”的结构雏形，内容颗粒度整体可控

结论：当前文档体系不是混乱状态，而是“已有框架，但缺少显式治理规则”。

## 2.2 当前主要问题

### 2.2.1 目录规则未完全统一

目前虽然大方向按 `需求 / 设计 / 开发` 分层，但在同一层内部还存在以下不一致：

- 有的阶段目录下只有主文档，有的阶段目录下又继续分成 `前端设计 / 后端设计`
- 有的总览文档放在一级目录，有的主题总览放在阶段目录内
- `开发` 层目前只覆盖 `01-单表单编辑器`，后续若继续扩展，缺少统一模板

### 2.2.2 文档命名风格不统一

当前同时存在以下命名方式：

- `需求拆分.md`
- `表单编辑器需求拆解.md`
- `第一阶段需求拆分（单表表单编辑与填报）`
- `单表单编辑器开发任务计划-V2.md`
- `表单领域重构草案.md`

主要问题不是“命名不好”，而是同类文档没有统一前缀和后缀，导致无法仅通过文件名识别其文档角色、阶段、状态。

### 2.2.3 文档角色边界不够清晰

从现有内容看，至少存在以下几类文档：

- 业务总览类
- 阶段需求类
- 架构总设计类
- 专题技术设计类
- 开发计划类
- 讨论草案类

但这些角色尚未被制度化定义，导致后续容易出现：

- 需求文档写入过多实现细节
- 设计文档重复描述需求背景
- 开发计划文档再次定义技术方案
- 草案长期存在却没有转正或归档

### 2.2.4 链接规范存在风险

当前文档中已经出现本地绝对路径引用，而且机器路径不一致，例如：

- `/Users/jia/...`
- `/Users/techbosch/...`

这类链接在多人协作、代码托管平台、不同开发机环境下都容易失效，应视为禁止项。

### 2.2.5 文档状态缺少统一标识

当前文件名中出现了 `V2`、`草案` 等状态表达，但没有统一规则，后续容易产生以下问题：

- 无法判断哪份是当前生效版本
- 无法区分“讨论中”“评审通过”“已废弃”
- 同一主题可能持续叠加 `V2/V3/最终版/重构版`

## 3. 结构清晰度判断

结论：当前文档结构“基础清晰，但不够稳定”。

具体判断如下：

- 从一级目录看是清晰的：`需求 / 设计 / 开发` 分层合理
- 从阶段划分看基本清晰：编号目录使阶段顺序和依赖关系可读
- 从新增扩展角度看还不够清晰：缺少统一的文档分类、命名、状态、索引规范

因此，当前结构适合继续沿用，但不建议继续无约束增长。下一步不应推翻重建，而应在现有结构上补齐治理规则。

## 4. 推荐文档体系

## 4.1 一级目录约束

`docs` 下只保留以下一级分类：

- `docs/需求`
- `docs/设计`
- `docs/开发`
- `docs/规范`
- `docs/归档`

说明：

- `需求` 只回答做什么、为什么做、范围边界与验收标准
- `设计` 只回答怎么设计、为什么这样设计、关键权衡和约束
- `开发` 只回答怎么落地、怎么排期、怎么验收、怎么推进
- `规范` 存放跨阶段、跨模块长期有效的约束性文档
- `归档` 存放废弃方案、历史版本、阶段性草案，避免污染主路径

## 4.2 二级目录约束

阶段型文档统一按“阶段编号 + 能力名称”建目录，例如：

```text
docs/
├── 需求/
│   ├── 00-总览/
│   ├── 01-单表单编辑器/
│   ├── 02-单表单填报/
│   └── 03-多表单扩展/
├── 设计/
│   ├── 00-总览/
│   ├── 01-单表单编辑器/
│   ├── 02-单表单填报/
│   └── 03-多表单扩展/
├── 开发/
│   ├── 01-单表单编辑器/
│   ├── 02-单表单填报/
│   └── 03-多表单扩展/
├── 规范/
└── 归档/
```

补充约束：

- `00-总览` 用于存放跨阶段总览文档
- 同一阶段在 `需求 / 设计 / 开发` 三层中应尽量保持相同编号与命名
- 若某阶段暂无开发文档，可以缺省目录，但命名规则仍应预留

## 4.3 阶段目录内的推荐分层

单个阶段目录建议最多分为以下三类：

- 主文档
- 子专题文档
- 附件/图示

推荐结构：

```text
docs/设计/01-单表单编辑器/
├── README.md
├── 总体设计.md
├── 前端设计/
├── 后端设计/
└── assets/
```

说明：

- `README.md` 作为该目录索引，说明本阶段有哪些文档、阅读顺序是什么、当前以哪份主文档为准
- `总体设计.md` 负责收敛关键设计结论
- `前端设计/`、`后端设计/` 只放专题细化方案
- `assets/` 放 mermaid 源图之外的图片、附件、导图

## 5. 文档分类规范

## 5.1 需求文档

需求文档分为以下三类：

### 5.1.1 总览需求

用于回答产品目标、阶段边界、里程碑和能力地图。

命名建议：

- `MVP总览.md`
- `阶段路线图.md`
- `规则体系总览.md`

### 5.1.2 阶段需求

用于描述某一阶段要交付的业务能力、范围、验收标准、非范围。

命名建议统一为：

- `阶段需求.md`

不建议同类文档混用：

- `需求拆分.md`
- `需求拆解.md`
- `需求说明.md`

除非它们在角色上确实不同。

### 5.1.3 专题需求

用于描述某一个能力点的专项需求，例如规则引擎、打印模板、明细表交互。

命名建议：

- `<专题名>需求.md`

例如：

- `交互规则需求.md`
- `业务规则需求.md`

## 5.2 设计文档

设计文档分为以下三类：

### 5.2.1 架构总设计

面向全局架构、上下文划分、核心原则、技术基线。

命名建议：

- `总体架构设计.md`
- `后端总体架构设计.md`
- `前端总体架构设计.md`

### 5.2.2 阶段总体设计

面向某阶段的完整设计收敛，包含输入文档、关键约束、模块边界、核心流程。

命名建议：

- `总体设计.md`

### 5.2.3 专题设计

面向单一问题的专项设计，例如持久化方案、拖拽落点判定、规则编译方案。

命名建议：

- `<专题名>设计.md`
- `<专题名>方案.md`

两者二选一，不建议并存。

建议优先使用：

- `设计` 用于相对稳定、可长期引用的正式文档
- `方案` 用于某个具体技术问题的可选实现收敛

## 5.3 开发文档

开发文档分为以下三类：

### 5.3.1 开发计划

用于任务拆解、迭代规划、排期、验收项映射。

命名建议：

- `开发计划.md`
- `迭代计划.md`

不建议持续叠加 `V2/V3` 到文件名；若更新，优先在文档头部维护版本记录。

### 5.3.2 实施说明

用于说明迁移步骤、联调说明、上线准备、风险清单。

命名建议：

- `实施说明.md`
- `联调说明.md`
- `上线清单.md`

### 5.3.3 技术讨论草案

用于临时分析、重构思路、方案预研。

命名建议：

- `<主题名>草案.md`

约束：

- 草案文档必须标注状态和截止时间
- 评审通过后应转正到 `需求 / 设计 / 开发 / 规范`
- 过期草案转移到 `docs/归档`

## 6. 命名规范

## 6.1 通用命名规则

- 文件名使用中文语义化命名，避免无信息量命名
- 同一目录下的同类文档必须使用统一后缀
- 文件名不写阶段序号，阶段信息由目录承载
- 避免在文件名中使用 `最终版`、`新版`、`重构版`
- 避免随意追加 `V2/V3/V5`

推荐：

- `阶段需求.md`
- `总体设计.md`
- `开发计划.md`
- `表单结构持久化设计.md`

不推荐：

- `需求拆分.md`
- `单表单编辑器开发任务计划-V2.md`
- `重构版-最终版.md`

## 6.2 状态表达规则

文档状态放在文档头部，不放在文件名中。

建议统一增加文档元信息：

```md
# 文档标题

## 元信息
| 字段 | 内容 |
|---|---|
| 状态 | 草案 / 评审中 / 已定稿 / 已归档 |
| 负责人 | xxx |
| 创建日期 | 2026-03-19 |
| 最后更新 | 2026-03-19 |
| 适用范围 | 01-单表单编辑器 |
| 关联文档 | 阶段需求、总体设计、开发计划 |
```

## 7. 文档内容边界

## 7.1 需求文档必须包含

- 背景与目标
- 范围与非范围
- 角色与场景
- 功能需求
- 验收标准
- 风险与待确认项

## 7.2 设计文档必须包含

- 输入文档
- 设计目标与约束
- 关键结论
- 备选方案与取舍
- 数据结构或模块边界
- 核心流程
- 风险与未决问题

## 7.3 开发文档必须包含

- 设计输入来源
- 任务拆解
- 里程碑或迭代安排
- 验收映射
- 风险与依赖
- 测试与联调要求

## 7.4 明确禁止的内容混杂

- 需求文档中禁止写大量类、表、接口实现细节
- 设计文档中禁止重新定义业务范围并覆盖需求结论
- 开发计划中禁止引入未经设计评审确认的核心架构决策

## 8. 链接与引用规范

- 禁止使用本地绝对路径，如 `/Users/...`
- 优先使用仓库相对路径，例如 `../需求/01-单表单编辑器/阶段需求.md`
- 引用上游文档时，要写清“本文以哪几份文档为输入”
- 若引用的文档是当前主依据，应在 `README.md` 或元信息中标注
- 同一主题如存在“总文档 + 子文档”，子文档必须回链主文档

## 9. 维护规范

## 9.1 新增文档前的判断顺序

新增文档前必须先判断：

1. 现有文档是否可增量补充，而不是新开一份
2. 新内容属于需求、设计、开发还是规范
3. 新内容是主文档、专题文档还是临时草案
4. 是否需要在对应目录 `README.md` 中登记

## 9.2 变更规则

- 小范围补充优先直接更新原文档
- 结构性变化才新增专题文档
- 主文档被替代时，应在原文档顶部标注“已被 XXX 替代”
- 废弃文档不删除，迁入 `docs/归档`

## 9.3 目录索引规则

每个阶段目录建议维护一个 `README.md`，至少包含：

- 阶段目标
- 推荐阅读顺序
- 当前主文档列表
- 已归档/已废弃文档说明

## 11. 结合当前仓库的落地建议

建议按以下优先级逐步治理，而不是一次性重构所有历史文档：

1. 先新增本规范文档，作为后续新增文档的统一依据
2. 在 `docs/需求`、`docs/设计`、`docs/开发` 下逐步补充 `README.md`
3. 统一清理所有本地绝对路径引用
4. 对高频主文档补充“元信息”区块，明确状态和关联关系
5. 后续新增文档严格按“主文档 / 专题文档 / 草案文档”三类落位

## 12. 最终约束清单

后续新增文档必须满足以下要求：

- 必须先判断所属分类：需求、设计、开发、规范、归档
- 必须放入对应阶段目录，不得随意平铺在一级目录
- 必须使用统一命名，不以 `V2/V3/最终版` 作为主要版本管理手段
- 必须在文档头部声明状态、负责人、时间、关联文档
- 必须写明输入来源和输出目标
- 必须避免与现有主文档重复造轮子
- 必须使用相对路径引用，不得写本地绝对路径
- 草案必须可转正、可归档，不能长期悬空

结论：本仓库当前文档体系可以继续沿用“按阶段分层”的主框架，但后续需要通过“统一角色、统一命名、统一状态、统一索引、统一归档”来保证长期可维护性。
